## 1. What each challenge does, step by step

### 1.0 Service-level description

- "Users can complete a Face Liveness check by taking a short video selfie where they follow a series of prompts intended to verify their presence." "When using FaceMovementAndLightChallenge the user's face moves into the oval displayed on their device, the Amplify SDK displays a sequence of colored lights on the screen. It then securely streams the selfie video to the cloud APIs. Alternatively, when using FaceMovementChallenge, the user's face moves into the oval displayed on their device, but there are no sequence of colored lights." — https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness.html
- AI Service Card: "(1) The liveness check requires the user move their face into an oval and hold still for a color sequence, which is recorded as a video by the frontend SDK. (2) The video is sent to the backend API and passed through a series of checks to validate successful completion. (3) A series of models check that the face is not a spoof, e.g., a photograph of a face, a full 3D face mask, a virtual injection attack. (4) If any of the aforementioned checks do not pass, or pass with low confidence, the API returned confidence score is reduced. (5) Different frames of the video are analyzed for quality. The frame with the highest quality score is returned as the face reference image. (6) A series of audit images, configurable by customers, between 0 and 4 are also returned." — https://docs.aws.amazon.com/ai/responsible-ai/rekognition-face-liveness/overview.html
- Three API calls: backend `CreateFaceLivenessSession` -> client `StartFaceLivenessSession` (WebSocket event stream, called by the Amplify component) -> backend `GetFaceLivenessSessionResults`. — https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-programming-api.html
- Transport: `StartFaceLivenessSession` "supports the websockets and the AWS SDK for JavaScript"; the request carries headers `x-amz-rekognition-streaming-liveness-session-id`, `-video-width`, `-video-height`, `-challenge-versions`, and a body event stream of `ClientSessionInformationEvent` and `VideoEvent`. — https://docs.aws.amazon.com/rekognition/latest/APIReference/API_rekognitionstreaming_StartFaceLivenessSession.html
- Actual WebSocket URL (Android): `wss://streaming-rekognition.<region>.amazonaws.com:443/start-face-liveness-session-websocket?session-id=…&video-width=…&video-height=…&challenge-versions=…&precheck-view-enabled=0|1&attempt-count=N`, SigV4-presigned. — ANDP `service/RunFaceLivenessSession.kt` (`buildWebSocketEndpoint`). Web adds the same `attempt-count` / `precheck-view-enabled` query parameters through a middleware; attempt-count resets after 5 minutes (`DEFAULT_ATTEMPT_COUNT_TIMEOUT = 300000`). — WEB `service/utils/TelemetryReporter/TelemetryReporter.ts`
- `ChallengeVersions` header: "String containing comma separated list of challenge versions supported by client", pattern `^([a-zA-Z]{10,}_\d+\.\d+\.\d+){1}(,…)*`. — StartFaceLivenessSession page above. The web client sends `FaceMovementAndLightChallenge_2.0.0,FaceMovementChallenge_1.0.0` (`SUPPORTED_CHALLENGES` / `queryParameterString`). — WEB `service/utils/constants.ts`. iOS also uses `.faceMovementAndLightChallenge("2.0.0")` and `.faceMovementChallenge("1.0.0")` — IOS `Views/Liveness/FaceLivenessDetectionView.swift` L445-455.
- Server replies with a `ServerSessionInformationEvent` whose `SessionInformation.Challenge` is a union: `FaceMovementAndLightChallenge` (`OvalParameters`, `LightChallengeType` = `SEQUENTIAL`, `ChallengeConfig`, `ColorSequences[]`) or `FaceMovementChallenge` (`OvalParameters`, `ChallengeConfig` only). The public HTML docs still list only the light member of `ServerChallenge` (https://docs.aws.amazon.com/rekognition/latest/APIReference/API_rekognitionstreaming_ServerChallenge.html), but the SDK model has both: `FaceMovementServerChallenge { OvalParameters, ChallengeConfig }` and `ClientChallenge.FaceMovementChallengeMember` — `@aws-sdk/client-rekognitionstreaming` 3.1135.0 `dist-types/models/models_0.d.ts`. The response stream also has a `ChallengeEvent {Version, Type}` member; Android notes "For the 1.0.0 version of FaceMovementAndLight challenge, backend doesn't send a ChallengeEvent so we need to manually check and set it". — ANDP `http/LivenessWebSocket.kt` L177-195.

### 1.1 FaceMovementAndLightChallenge, from the person's point of view (web SDK state machine)

State names are from WEB `service/machine/machine.ts`; hint strings from WEB `displayText.ts`.

1. Camera check (`initCamera.cameraCheck`): `getUserMedia({video: {width:{min:320,ideal:640}, height:{min:240,ideal:480}, frameRate:{min:15,ideal:30,max:60}, facingMode:'user'}, audio:false})` — WEB `utils/helpers.ts` (`STATIC_VIDEO_CONSTRAINTS`). Virtual cameras (label contains "virtual") are excluded; at least one track must report `frameRate >= 15` or the error "No camera found with more than 15 fps" -> `CAMERA_FRAMERATE_ERROR`. — `machine.ts` `checkVirtualCameraAndGetStream`.
2. WebSocket opened (`initWebsocket`) with `VideoWidth`/`VideoHeight` = the `<video>` element's intrinsic size; 10 s connection timeout (`CONNECTION_TIMEOUT = 10_000`, WEB `constants.ts`; the Amplify troubleshooting doc still says "will time out after 5 seconds", https://ui.docs.amplify.aws/react/connected-components/liveness/troubleshooting). The machine polls every 100 ms until `ServerSessionInformationEvent` arrives.
3. "Get ready"/start screen (`start`): hint "Center your face" with a static oval (width = 0.5 × video width via `drawStaticOval`/`ratioMultiplier: 0.5`, WEB `liveness.ts`), photosensitivity warning ("This check flashes different colors. Use caution if you are photosensitive."), button "Start video check". Can be skipped with `disableStartScreen`. BlazeFace model loads here.
4. `detectFaceBeforeStart`: loop until exactly one face (`FACE_IDENTIFIED`); hints "Move face in front of camera" / "Ensure only one face is in front of camera".
5. `detectFaceDistanceBeforeRecording`: computes `calibratedPupilDistance / staticOvalWidth` and requires it `< FaceDistanceThresholdMin` (first pass) — the face must be FAR enough; if not, hint "Move back". On re-check the looser `FaceDistanceThreshold` is used (`reduceThreshold`). — WEB `liveness.ts` `isFaceDistanceBelowThreshold`. (Contrast: in the docs `FACE_DISTANCE_ERROR` means "the user moved their face too close to the camera before the check started". — https://ui.docs.amplify.aws/react/connected-components/liveness#error-states)
6. `recording`: `MediaRecorder.start(1000)` (1-second chunks) starts; `ovalDrawing` detects the initial face, draws the SERVER-supplied oval (`OvalParameters.CenterX/CenterY/Width/Height`, in video pixels, mirrored for display: `flippedCenterX = videoWidth - CenterX`), 5 s runtime timeout "Client failed to draw oval."; then waits for the first chunk ("Client failed to start recording." after 5 s).
7. On first chunk it sends `ClientSessionInformationEvent` #1 (`createSessionStartEvent`): `{ChallengeId (client uuid v4), VideoStartTimestamp, InitialFace{BoundingBox (normalised 0-1, left flipped back to un-mirrored coordinates), InitialFaceDetectedTimestamp}}`. `VideoStartTimestamp` is "0.73 × (recorder.onstart time − start() call time) + start() call time" — "This calculation is provided by Science team after doing analysis of unreliable .onstart() timestamp". — WEB `StreamRecorder.ts` `getRecordingStartTimestamp`.
8. `ovalMatching`/`checkMatch` loop (re-evaluated every 1 ms): hint "Move closer" (also shown for `CANT_IDENTIFY`/`TOO_MANY`; comment: "we are defaulting to the TOO_FAR text (for now)"), a11y text "Face is not in the oval, center your face to the camera." for `OFF_CENTER`, plus a progress bar (`faceMatchPercentage`, starts at 25 %). Timeout = `ChallengeConfig.OvalFitTimeout` (fallback `DEFAULT_FACE_FIT_TIMEOUT = 7000` ms) -> `TIMEOUT` with "Face didn't fit inside oval in time limit. Try again and completely fill the oval with face in it." and WebSocket close code 4001.
9. On `MATCHED`: records `startFace`/`endFace` (timestamps of the matching detections), `handleChallenge` -> `delayBeforeFlash` (1000 ms, hint "Hold still") -> `flashFreshnessColors`.
10. Colour sequence plays full screen over the video (see section 3); on each colour change it sends `ClientSessionInformationEvent` with `ColorDisplayed{CurrentColor{RGB}, PreviousColor{RGB}, SequenceNumber, CurrentColorStartTimestamp}`. Hint stays "Hold still". There is NO client-side check that the face stays in the oval during the flash on web (the machine simply awaits `freshnessColorsComplete`); iOS does stop the flash if the face leaves ("During the freshness (color) check, a face that leaves can no longer produce a valid color sequence, so we stop the color flash and send the flow back to oval matching" — IOS `FaceLivenessDetectionViewModel+FaceDetectionResultHandler.swift`).
11. `success` -> `uploading.pending`: stops the recorder, requires >0 chunks ("Video chunks not recorded successfully."), sends `ClientSessionInformationEvent` #last (`createSessionEndEvent`): `{ChallengeId, InitialFace (again), TargetFace{BoundingBox = the oval's box normalised, FaceDetectedInTargetPositionStartTimestamp, …EndTimestamp}, VideoEndTimestamp}`, then an EMPTY `VideoEvent` ("server expects an empty chunk on 'stopStream' event", WEB `createRequestStreamGenerator/utils.ts`). Hint "Verifying...". Then it waits (polling 100 ms) for the server `DisconnectionEvent` ("Disconnection events may indicate processing is complete at the server side" — SDK model), calls `onAnalysisComplete`, and the backend calls `GetFaceLivenessSessionResults`.
12. Timing: FAQ "In the best case, the latency is 5s. In average case, we expect it to be about 7s. In the worst case, the latency is 11s." — https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-faq.html

Native SDKs follow the same skeleton: Android sends `InitialFaceDetected` as soon as the distance check passes and the oval is created, `FaceTargetChallengeResponse` + empty `VideoEvent` at the end (AND `state/LivenessState.kt`); iOS: `pendingFacePreparedConfirmation` (face distance ≤ `FaceDistanceThreshold`, else "faceTooClose") -> 1 s -> `recording` -> draw oval -> `sendInitialFaceDetectedEvent` -> `awaitingFaceInOvalMatch` -> `faceMatched` -> 1 s -> `displayingFreshness` -> `completedDisplayingFreshness` -> `awaitingDisconnectEvent` (IOS `LivenessStateMachine.swift`, `…+FaceDetectionResultHandler.swift`). iOS also has hints `moveToDimmerArea`/`moveToBrighterArea`; web computes an illumination histogram only when NO face is found and shows "Move to dimmer area"/"Move to brighter area" (WEB `liveness.ts` `estimateIllumination`).

### 1.2 FaceMovementChallenge

Identical up to step 9, then `handleChallenge` -> `success` directly (`{ target: 'success', cond: 'isFaceMovementChallenge' }`, `machine.ts`); no `ColorDisplayed` events; `ClientSessionInformationEvent.Challenge.FaceMovementChallenge` carries only `{ChallengeId, VideoStartTimestamp, VideoEndTimestamp, InitialFace, TargetFace}` (SDK model `FaceMovementClientChallenge`). The photosensitivity warning is not rendered ("Applies only to Face Movement and Light Challenge; PhotosensitiveWarning will not render with the Face Movement Challenge" — https://ui.docs.amplify.aws/react/connected-components/liveness). Camera selection: on web, the camera picker is shown on mobile only for this challenge (`allowDeviceSelection = … (!isMobileScreen || isFaceMovementChallenge)`, WEB `LivenessCheck/LivenessCameraModule.tsx`); on Android/iOS `challengeOptions` lets you pick `Camera.Back` for `FaceMovement` only ("you can configure the FaceMovement challenge to use either the device's front-facing camera or back-facing camera" — https://ui.docs.amplify.aws/android/connected-components/liveness/customization). AWS: "'FaceMovementChallenge' … allows users to complete checks using the front or back facing camera." — https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-rekognition-face-liveness-accuracy-improvements-challenge-setting/. Android still forces max brightness and portrait lock for both challenges (AND `ui/FaceLivenessDetector.kt` L150-152).

## 2. `ChallengeConfig` and session settings

### 2.1 `CreateFaceLivenessSession` (backend)

- `Settings.AuditImagesLimit`: "between 0 and 4. By default, it is set to 0. The limit is best effort and based on the duration of the selfie-video."
- `Settings.ChallengePreferences[]`: "An ordered list of preferred challenge type and versions"; `Type` valid values `FaceMovementAndLightChallenge | FaceMovementChallenge` (required); `Versions{Minimum, Maximum}` optional. "if no parameter is provided, then the 'FaceMovementAndLightChallenge' settings is applied by default."
- `Settings.OutputConfig{S3Bucket, S3KeyPrefix}`; `KmsKeyId`; `ClientRequestToken` (idempotency, 1-64 chars).
- `SessionId`: "A new sessionID must be used for every Face Liveness check. If a given sessionID is used for subsequent Face Liveness checks, the checks will fail. Additionally, a SessionId expires 3 minutes after it's sent, making all Liveness data associated with the session … unavailable."
— https://docs.aws.amazon.com/rekognition/latest/APIReference/API_CreateFaceLivenessSession.html, https://docs.aws.amazon.com/rekognition/latest/APIReference/API_ChallengePreference.html
- `GetFaceLivenessSessionResults`: `Confidence` float 0-100; `Status` ∈ `CREATED | IN_PROGRESS | SUCCEEDED | FAILED | EXPIRED`; `Challenge{Type, Version}`; "In case the reference image is not returned, it's recommended to retry the Liveness check." — https://docs.aws.amazon.com/rekognition/latest/APIReference/API_GetFaceLivenessSessionResults.html

### 2.2 `ChallengeConfig` (server -> client, inside `ServerSessionInformationEvent`)

Documented at https://docs.aws.amazon.com/rekognition/latest/APIReference/API_rekognitionstreaming_ChallengeConfig.html — "Configuration options for Face Liveness challenges performed at the client side." All optional in the wire schema; AWS publishes NO defaults. The "observed value" column is the fixture in the web SDK's unit tests (`mockFaceMovementAndLightSessionInfo`, WEB `service/utils/__mocks__/testUtils.ts`); the float32 artefacts (0.4000000059604645, 1.6180000305175781) strongly suggest these were copied from a real server response, but AWS does not document them and they can change server-side at any time.

| Field | Type / documented range | Documented description | Observed value | What the clients do with it |
|---|---|---|---|---|
| `BlazeFaceDetectionThreshold` | Float 0-1 | "Threshold for face detection done using blaze face." | 0.75 | Android: detections with sigmoid score below it are dropped (AND `ml/FaceDetector.kt` L50). iOS: same (`FaceDetectorShortRange+Model.swift` L115-129). Web: NOT used (tfjs face-detection defaults). |
| `FaceDistanceThresholdMin` | Float 0-1 | "Threshold for the minimum distance that face can be from the camera before face oval match challenge starts." | 0.4000000059604645 | Web pre-record check: `calibratedPupilDistance / staticOvalWidth < FaceDistanceThresholdMin` must hold on the first pass (`isFaceDistanceBelowThreshold`). | `FaceDistanceThreshold` | Float 0-1 | "Threshold for face distance threshold face liveness challenge." | 0.4000000059604645 | Web: used on the second, relaxed distance pass (`reduceThreshold`). iOS: `face.faceDistance <= distanceThreshold` gate before recording. Related server-supplied values:
- `OvalParameters {CenterX, CenterY, Width, Height}` — floats 0-9999 in video pixel coordinates; "The parameters needed for an oval to display and to complete oval match challenge." `TargetFace` docs: "generated using the random offsets provided by the server to the client at session start." — https://docs.aws.amazon.com/rekognition/latest/APIReference/API_rekognitionstreaming_OvalParameters.html, …/API_rekognitionstreaming_TargetFace.html. The pre-check static oval on the client is centred with seeds (7/16..9/16 of width/height), width `0.8 × videoWidth` (portrait; landscape uses `¾·height`), height `1.618 × width` (WEB `getStaticLivenessOvalDetails`; AND `getStaticOvalWidth` r = 0.8). FAQ: "Can I change the location of the oval and colored lights? No."
- `LightChallengeType`: only `SEQUENTIAL`.
- `ColorSequences[]`: see section 3.
- Web hard-coded constants (not from server): `PUPIL_DISTANCE_WEIGHT = 2.0`, `FACE_HEIGHT_WEIGHT = 1.8`, `FACE_MATCH_WEIGHT_MIN/MAX = 0.25/0.75`, `TICK_RATE = 10` ms, `TIME_SLICE = 1000`, `REQUEST_EXPIRY = 299` s presigned URL, `CONNECTION_TIMEOUT = 10000` — WEB `constants.ts`.

Client-side event field constraints (docs): all epoch timestamps must be in `[1640995200000, 2272147200000]` (2022-01-01 … 2042-01-01); `SequenceNumber` 0-50; `ChallengeId` UUID; `BoundingBox` ratios of frame size ("if the input image is 700x200 pixels, and the top-left coordinate of the bounding box is 350x50 pixels, the API returns a left value of 0.5"). — https://docs.aws.amazon.com/rekognition/latest/APIReference/API_rekognitionstreaming_ColorDisplayed.html, …/API_rekognitionstreaming_InitialFace.html, SDK model.

Clock skew: "any clock skew of 5 minutes or larger will be rejected by default" (`InvalidSignatureException: Signature not yet current`), `systemClockOffset` config exists to compensate — https://ui.docs.amplify.aws/react/connected-components/liveness/troubleshooting. Android adjusts its dates from the server `Date` header and only trusts diffs under 4 minutes (`FOUR_MINUTES`, ANDP `LivenessWebSocket.kt`).

## 3. The colour sequence

Wire definition: `ColorSequence { FreshnessColor{RGB:[r,g,b]}, DownscrollDuration (Float, 0-1000 ms) "for which a given color … will down-scroll before taking over full screen", FlatDisplayDuration (Float, 0-1000 ms) "for which a given flat color … will be displayed on the full screen" }`. — https://docs.aws.amazon.com/rekognition/latest/APIReference/API_rekognitionstreaming_ColorSequence.html

How many / which: AWS does not document the list. The web SDK test fixture, annotated "// sequence values from service", is 8 entries: `rgb(0,0,0)` flat 75 ms, then `rgb(0,255,0)`, `rgb(255,0,255)`, `rgb(255,0,0)`, `rgb(0,0,255)`, `rgb(255,0,0)`, `rgb(0,255,0)`, `rgb(255,0,0)` each downscroll 475 ms / flat 0 (≈ 3.4 s total). — https://github.com/aws-amplify/amplify-ui/blob/main/packages/react-liveness/src/components/FaceLivenessDetector/service/utils/ColorSequenceDisplay/__tests__/ColorSequenceDisplay.test.ts. That is a fixture, not a spec; the order is presumably randomised per session (the docs say "Used to generate a list of color sequences", and the client does nothing but replay it). `SequenceNumber` max 50 bounds the length. FAQ: "the user experience displays approximately two colors per second, which complies with the recommendation of limiting colors to three per second" (WCAG 2.1) — https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-faq.html — consistent with 475 ms per colour.

How each colour is rendered (all three clients agree):
- A colour with `FlatDisplayDuration > 0` is shown as a full-screen flat fill for that duration; a colour with `FlatDisplayDuration == 0` "down-scrolls": the new colour fills the screen from the top, `heightFraction = elapsed / DownscrollDuration`, the previous colour remains below (web `fillFractionalContext`; Android `FreshnessChallenge` draws `currentColor` rect height `size.height × completion` and `previousColor` beneath; iOS `FreshnessView` two stacked rectangles). Android chooses per entry: `shouldScroll = flatDisplayDuration == 0f; duration = shouldScroll ? downscrollDuration : flatDisplayDuration` (ANDP `service/RunFaceLivenessSession.kt` L96-110).
- The fill is translucent over the live camera and the oval: alpha 0.9 for the first scene, 0.75 afterwards; the oval area is filled at 0.75 with an 8 px white stroke, the surround at 0.9 (WEB `liveness.ts` `INITIAL_ALPHA/SECONDARY_ALPHA`, `fillOverlayCanvasFractional`; AND `FreshnessState.FIRST_SCENE_ALPHA = 255·0.90`, `REMAINING_SCENE_ALPHA = 255·0.75`; IOS `Freshness(initialAlpha: 0.9, secondaryAlpha: 0.75)`).
- Tick: web `setTimeout` every 10 ms (`TICK_RATE`), iOS `tickRate 0.01`, Android per display frame (`withFrameMillis`). Web starts the flash 1000 ms after the match; hint "Hold still".
- Brightness: "The Face Liveness mobile SDKs (for Android and iOS) automatically adjust the brightness when the check is initiated. However, for the web SDK there are limitations on webpages that prevent automatic brightness adjustment." — FAQ. Android sets `BRIGHTNESS_OVERRIDE_FULL` + `FLAG_KEEP_SCREEN_ON` (AND `ui/AlwaysOnMaxBrightnessScreen.kt`); iOS `UIScreen.main.brightness = 1.0` (IOS `FaceLivenessDetectionView.swift` L288-305).

What the SDK records/sends: one `ClientSessionInformationEvent` per colour change: `ColorDisplayed { CurrentColor{RGB}, PreviousColor{RGB}, SequenceNumber, CurrentColorStartTimestamp (epoch ms, device clock, `Date.now()` at the tick that started the colour) }` — WEB `createColorDisplayEvent`; Android `onColorDisplayed(currentColor, previousColor ?: currentColor, sceneIndex, currentTime)`. Web sends an additional initial event (`isFirstTick`) with prev == current for index 0.

What the service checks: not documented beyond "A series of models check that the face is not a spoof" and that confounding variation includes "the bright sunlight reducing the visibility of different color lights reflected from the user's face" (Service Card) — i.e. the service correlates screen-reflected colour changes in the face region of the video against the reported colour timeline. The service also cross-checks client events: an observed server 400 reads "InitialFace is not same as received in previous event, baseObject: InitialFace(...) eventObject: InitialFace(...)" (https://github.com/aws-amplify/amplify-ui/issues/6397), so the `InitialFace` sent at start and at end must be byte-identical, and "Stream idle timeoutExceeded" is thrown "when the video stream is being idle for more than 15 seconds" (AWS staff, https://github.com/aws-amplify/amplify-ui/issues/6433).

## 4. Security and assurance

- Attack classes: "Liveness is designed to detect presentation and digital injection attacks… Examples of presentation attacks include printed photos, digital photos, digital videos, or 3D masks which are physically presented to a camera. Digital injection attacks are spoofs that bypass the camera, such as pre-recorded or deepfake videos." "designed to return low confidence scores for faces from 2D photos, 3D full-face masks, digital photos or videos displayed on a device screen, and pre-recorded videos." — Service Card https://docs.aws.amazon.com/ai/responsible-ai/rekognition-face-liveness/overview.html
- Threshold semantics: "a moderate confidence score threshold (e.g., 50 or 60) may be suitable to detect presentation attacks and some digital injection attacks. Alternatively, a high confidence score threshold (e.g., 80 or 90) may be suitable to detect sophisticated digital injection attacks, such as deep fake or pre-recorded videos." — Service Card.
- Difference between the two challenges (the only AWS statements): "The 'FaceMovementAndLightChallenge' setting delivers the highest accuracy for Rekognition Liveness by requiring users to move their face toward the screen and hold still for a series of flashing lights. We recommend that customers use this default setting. Alternatively, customers can enable the 'FaceMovementChallenge' setting, which reduces the check time by several seconds by eliminating the flashing lights. While 'FaceMovementAndLightChallenge' remains the best setting to maximize accuracy, 'FaceMovementChallenge' allows customers to prioritize faster liveness checks. When selecting between these settings, customers should consider their use case requirements including expected attack types, desired false accept and false reject rates, and also implement additional checks such as geolocation (e.g. based on IP), One Time Pass codes (OTPs), etc. Customers should make this decision after testing Liveness performance with various confidence score thresholds depending on their use case. Customers are responsible to implement controls to secure the device of which the video is sent from" — https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-shared-responsibility-model.html (same wording on face-liveness.html). AWS never says which attack the light defeats, and publishes no FAR/FRR for the no-light challenge; the only statement of weakness is "prioritize faster speed of liveness checks over accuracy".
- iBeta / ISO 30107-3: "iBeta … used their … Presentation Attack Detection (PAD) framework to conduct two tests (Level 1 and Level 2) … in accordance with ISO/IEC 30107-3. … For Level 1 testing, 6 different attack types were used across varying categories of printed photos, 3D masks, photos on smart phones, and videos on laptops. 900 attack attempts resulted in a true rejection rate (TRR) of 100% at a confidence score threshold of 50. In that same test, 300 genuine user attempts resulted in a true acceptance rate (TAR) of 100% at a confidence score threshold of 50. For Level 2 testing, 5 different attack types were used across silicone mask, latex mask, 3D contoured mask, 3D printed mask, and 3D animation software. 750 attack attempts resulted in a TRR of 100% at a confidence score threshold of 50. In that same test, 250 genuine user attempts resulted in a TAR of 100%." — Service Card (letters dated 2023-09-11 and 2023-10-19). FAQ: "passed Level 1 and Level 2 iBeta Presentation Attack Detection (PAD) conformance testing with a perfect PAD score." Which challenge: the Service Card "applies to the release … current as of November 27, 2023" and describes only the oval + colour flow; `FaceMovementChallenge` v1.0.0 has release date 4/30/2025 in the versioning table (https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-update-guidelines.html). So the iBeta results cover the light challenge only (inference from dates; AWS has not published a PAD result for the no-light challenge). Note iBeta PAD Levels 1-2 are presentation attacks only; injection/deepfake claims are AWS's own.
- Shared responsibility: "The customer backend must identify the end user performing the Face Liveness challenge… The Face Liveness service does not distinguish between end users." Recommends STRIDE, digest/OAuth/OIDC auth of the customer's own create/get endpoints, and that "the third-party code/library/etc used is being actively maintained". — shared-responsibility page.
- Operational hardening: "Do not send or display the liveness check score on the user application. Only send a pass or fail signal." "Allow only five failed liveness checks in three minutes from a single device. After five fails, timeout the user for 30–60 minutes. If the pattern is seen 3–5 times repeatedly, block the user device." "Regularly run human review checks on audit images." — https://docs.aws.amazon.com/rekognition/latest/dg/recommendations-liveness.html
- Client anti-tamper: rejects virtual cameras by label (web), requires "Device should not be jail-broken or rooted", "No virtual camera or camera software." (requirements page). Old SDK versions "may be blocked for maintainability and security reasons"; major versions supported 120 days, minor 180 days — update-guidelines page.
- Product FAQ: "We do not recommend using Face Liveness and face matching in place of username/password… as a secondary or step-up method." — https://aws.amazon.com/rekognition/face-liveness/

## 5. Documented problems, limits and requirements

### 5.1 Environment
- "Users should complete the Face Liveness check in environments that aren't too dark or too bright and have fairly uniform lighting." "Users should increase their display screen's brightness to its maximum level when making checks on web browsers." — recommendations-liveness.html
- "Performing the face liveness check outdoors can result in unsuitable conditions such as the bright sunlight reducing the visibility of different color lights reflected from the user's face. As a consequence, there may be an increase in false rejections of genuine users. In these suboptimal conditions, a lower confidence score (e.g., 50 or 60) may be more effective"; indoors "a higher confidence score threshold (e.g., 80 or 90) may be more effective". Confounding variations: "(1) variations in lighting direction and intensity; (2) head pose; (3) camera focus and video capture imperfections; (4) video resolution; and (5) occlusions caused by masks, sunglasses, hands, cell phones, scarves, hats, or other objects." Performance "will vary depending on … device screen characteristics such as brightness, size, and resolution; and camera characteristics such as resolution, focal length, frame rate, and bit rate." — Service Card.
- Accessibility: "Offer an alternative face liveness verification path to your users if they are photo-sensitive or do not want to verify their face liveness using Rekognition." — recommendations. Photosensitivity warning text in every SDK.
- Fairness: AWS says it tests on datasets "with reliable demographic labels such as gender, age, and skin tone" and that "Face Liveness is designed to work well for all human faces" (Service Card); one user report in the iOS 18.4 idle-timeout thread claims it "seems highly occurs with brown skin face" (https://github.com/aws-amplify/amplify-ui/issues/6433, user comment, unverified, the thread concluded iOS 18.4 beta was the cause).

### 5.2 Device / browser minimums
- Developer guide: front camera; display refresh ≥ 60 Hz; screen ≥ 4 inches; not rooted/jailbroken; colour camera; no virtual camera; ≥ 15 fps; "Minimum video recording resolution: 480x640px"; webcam "mounted on top of the same screen"; bandwidth ≥ 100 kbps; "Latest three versions of major browsers, such as Google Chrome, Mozilla Firefox, Apple Safari, and Microsoft Edge." — https://docs.aws.amazon.com/rekognition/latest/dg/face-liveness-requirements.html. The Service Card and the web SDK error text say 320×240 ("Camera must support at least 320*240 resolution and 15 frames per second." — WEB `displayText.ts`), so the two AWS documents disagree (480×640 vs 320×240).
- Web runtime needs: `MediaRecorder` ("MediaRecorder is not supported by this browser" thrown otherwise), `ReadableStream`, WebSocket, and TensorFlow.js BlazeFace (`MediaPipeFaceDetector` short-range model 1.0.2) on the WASM backend with a CPU fallback when `WebAssembly` is absent (WEB `blazefaceFaceDetection.ts`, `support.ts`); model and `.wasm` are loaded from `https://cdn.liveness.rekognition.amazonaws.com/…` unless `faceModelUrl`/`binaryPath` override (self-hosting instructions: https://ui.docs.amplify.aws/react/connected-components/liveness/customization). Model load now has a 10 s timeout (3.6.7, PR #7005). Portrait only on mobile: `MOBILE_LANDSCAPE_ERROR` "Landscape orientation not supported"; detection via `matchMedia('(orientation: landscape)')` because "screen.orientation is not supported in Safari" (WEB `utils/device.ts`, `LivenessCheck.tsx`). "Android/Firefox and iOS flip the values of width/height returned from getUserMedia" (comment in `LivenessCameraModule.tsx`). Android SDK: API 24+ ("passed preliminary testing on API level 23 … not officially supported"); iOS 14+ — https://ui.docs.amplify.aws/android/connected-components/liveness. The FAQ: "Can I use Face Liveness feature without Amplify SDK? No, the Amplify SDK is required."
- Regions (FAQ): us-east-1, us-west-2, eu-west-1, ap-northeast-1, ap-south-1, sa-east-1, ap-southeast-5 (Malaysia), ap-southeast-7 (Thailand); the S3 bucket must be in the Face Liveness region.

### 5.4 Error states and what they mean
Web `LivenessErrorState` (https://ui.docs.amplify.aws/react/connected-components/liveness): `RUNTIME_ERROR` "error that occurs in the component runtime"; `SERVER_ERROR` "from the Rekognition streaming API or in the onAnalysisComplete callback"; `CONNECTION_TIMEOUT` "during the initial websocket connection"; `TIMEOUT` "when user attempted a liveness check" (face-in-oval); `FACE_DISTANCE_ERROR` "moved their face too close to the camera before the check started"; `CAMERA_ACCESS_ERROR`; `CAMERA_FRAMERATE_ERROR` "does not meet the minimum framerate"; `FRESHNESS_TIMEOUT` "timed out when attempting to determine freshness of the video via colors flashing" (defined but never raised by the current machine); `MOBILE_LANDSCAPE_ERROR`; `MULTIPLE_FACES_ERROR`; plus `DEFAULT_CAMERA_NOT_FOUND_ERROR` in code (WEB `service/types/error.ts`). Client `FaceMatchState`: `MATCHED, TOO FAR, CANNOT IDENTIFY, ONE FACE IDENTIFIED, TOO MANY FACES, OFF CENTER`.
Android `FaceLivenessDetectionException` subclasses: `SessionNotFoundException, AccessDeniedException, CameraPermissionDeniedException, SessionInterruptedException, SessionTimedOutException, UnsupportedChallengeTypeException ("Received an unsupported ChallengeType from the backend."), UserCancelledException, VideoEncodingException ("The device may not support video encoding"), VideoMuxingException, FaceInOvalMatchExceededTimeLimitException` — AND `model/FaceLivenessDetectionException.kt`. iOS `FaceLivenessDetectionError`: `.unknown, .sessionNotFound, .sessionTimedOut, .faceInOvalMatchExceededTimeLimitError, .accessDenied, .cameraPermissionDenied, .cameraNotAvailable, .userCancelled, .socketClosed, .invalidRegion, .validation, .internalServer, .throttling, .serviceQuotaExceeded, .serviceUnavailable, .invalidSignature` — https://ui.docs.amplify.aws/swift/connected-components/liveness.
Service: `ValidationException` (video quality/size invalid, container unsupported, "no person detected in video", session expired, S3 bucket wrong region, KMS invalid), `SessionNotFoundException`, `AccessDeniedException` 403, `ThrottlingException`/`ServiceQuotaExceededException` 429, `ServiceUnavailableException` 503, `InternalServerException` 500 — StartFaceLivenessSession page.

### 5.5 Confidence semantics
"Confidence: Probabalistic confidence score for if the person in the given video was live, represented as a float value between 0 to 100." — GetFaceLivenessSessionResults. "The minimum confidence score is 0, implying a spoof attack, and the maximum is 100, implying a genuine user." Recommended thresholds: 50/60 moderate (presentation attacks, outdoors), 80/90 high (injection/deepfake, well-lit indoor). "Amazon Rekognition Face Liveness itself does not independently determine if a face in the selfie video is real or a spoof attack." TAR/TRR "are generally inversely related." — Service Card. Retry semantics: new session per attempt; "Sessions are single-use; create a new one before retrying after errors" — Amplify docs. Web `maxFailedAttempts = 0` "as we are not allowing front end based retries for streaming" (`machine.ts`).

## 6. Why `FaceMovementChallenge` was added, and guidance

- Announcement 2025-07-03: "Previously, Rekognition Liveness only offered the 'FaceMovementAndLightChallenge' setting, but the new 'FaceMovementChallenge' setting reduces the check time by 3 seconds by eliminating the flashing lights… allows customers to prioritize faster liveness checks and allows users to complete checks using the front or back facing camera. The update also delivers improved accuracy across both settings." — https://aws.amazon.com/about-aws/whats-new/2025/07/amazon-rekognition-face-liveness-accuracy-improvements-challenge-setting/. Versioning table: `FaceMovementChallenge v1.0.0` release date 4/30/2025; `FaceMovementAndLightChallenge v1.0.0` 4/10/2023 (clients now send 2.0.0; web bumped in 3.4.1 on 2025-06-30, "feat(liveness): add support for face movement only/no light challenge" landed in 3.4.0 on 2025-06-27 — CHANGELOG + npm publish dates).
- AWS's stated rationale is speed and camera flexibility, not accessibility; the only accessibility-related statements are the WCAG 2.1 flash-rate claim for the light challenge and the recommendation to "Offer an alternative face liveness verification path to your users if they are photo-sensitive" (recommendations page). The Amplify docs merely note the photosensitivity warning is omitted for the no-light challenge.
- Guidance on choosing: only the shared-responsibility paragraph quoted in section 4 (accuracy vs speed, consider attack types and FAR/FRR, add geolocation/OTP, test thresholds on your own content, secure the device). Default is the light challenge.

## Things Lumiface will run into too

1. The oval-fit step needs a server-supplied oval (random centre) and thresholds, a client fit timeout (AWS: ≤ 10 s, default 7 s), a "too close before start" gate, a progress indicator, and a 1 s hold-still before the flash; users regularly hit the fit timeout ("Face didn't fit inside oval in time limit").
2. Colour flash: ~2 colours/s (475 ms scroll each) is what AWS calls WCAG-safe; a first dark "flat" frame; translucent (0.75-0.9 alpha) so the face stays visible; a photosensitivity warning and an alternative path; web cannot force brightness, so the app must tell users to max it, and bright sunlight washes the reflection out -> higher false rejects.
3. Timestamps: MediaRecorder's `onstart` is unreliable (AWS scales it by 0.73); colour-start timestamps come from the device clock; clock skew > 4-5 min breaks signing; every event carries epoch ms that the server cross-checks (InitialFace must be identical in start and end events).
4. Video transport: default browser MediaRecorder codecs differ (WebM/VP8-VP9 on Chrome/Firefox, fragmented MP4/H.264 on Safari, and Android Chrome 125 shipped a broken H.264 encoder); 1 s chunks at ~1 Mbps; cap total size (AWS 10 MB); a server idle timeout (AWS 15 s) and explicit close codes for cancel/timeout/runtime error.
5. Device gating: 15 fps minimum, 320×240 vs 480×640 minimum (AWS documents both), reject virtual cameras and landscape on mobile, exactly one face, and a get-ready screen (AWS says it measurably improves pass rates).
6. Platform quirks already hit by AWS: iOS point releases breaking MediaRecorder/codec output, iOS/Firefox-Android swapping width/height, Safari lacking `screen.orientation`, camera not released on unmount, CSS frameworks hiding the flash overlay, WASM/model CDN loading failures (add a load timeout and self-hosting option).
7. Scoring/ops: return pass/fail not the score, single-use sessions with a short expiry, rate-limit failed attempts per device (5 per 3 min), keep audit frames for human review, expect indoor vs outdoor to need different thresholds, and be explicit that a no-light mode trades assurance for speed (AWS has no PAD result for it).

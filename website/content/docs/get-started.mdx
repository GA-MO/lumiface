<Steps>
<Step>
## Run the server

```bash
cd server
uv sync
uv run python weights/download.py          # buffalo_l (~300MB) + MiniFASNet weights
cp .env.example .env                        # set BOOTSTRAP_API_KEY and ADMIN_API_KEY
uv run uvicorn app.main:app --host 0.0.0.0 --port 8000
```

The CVPR-2024 ResNet50 ONNX (94 MB) is not in git. Convert it once with
`uv run --with gdown --with torch --with onnx --with onnxscript python weights/convert_cvpr.py`, or set `CVPR_ENABLED=0` to run without it (weaker against bezel-free screen replay).

`GET /health` answers `{"ok": true, "presets": [...]}`. The first start creates a project named `default` with `BOOTSTRAP_API_KEY` and the `BOOTSTRAP_PRESET` preset.
</Step>
<Step>
## Enrol a subject

From your backend, where the API key lives:

```bash
curl -X POST localhost:8000/v1/subjects -H "X-API-Key: lf_sk_change-me" \
  -F external_id=E001 -F name="Person A" -F photo=@me.jpg
```

A frontal photo with one face. The server rejects it with a `reason_code` (`NO_FACE`, `POSE_NOT_FRONTAL`, `SPOOF`, ...) instead of enrolling a bad reference.

To enrol from the device's camera instead (`FaceFlow.enroll` / `flow="enroll"`), the backend mints a single-use token and the app presents it; the device still never holds the key:

```bash
curl -X POST localhost:8000/v1/subjects/tokens -H "X-API-Key: lf_sk_change-me" \
  -H "Content-Type: application/json" -d '{"external_id": "E001", "name": "Person A"}'
# → {"token": "…", "external_id": "E001", "expires_at": "…"}   pass it as enrolToken
```
</Step>
<Step>
## Pick a preset

```bash
curl -X PUT localhost:8000/v1/policy -H "X-API-Key: lf_sk_change-me" \
  -H "Content-Type: application/json" -d '{"preset": "balanced"}'
```

`balanced` is the phone-calibrated default. Use `emulator` on the Android emulator, `relaxed` while developing on a laptop (the flash check records scores without enforcing), `strict` for access control. See [Policy](/docs/server/policy).
</Step>
<Step>
## Run the example app

The examples run the real three-party flow. `examples/backend` is a ~100-line FastAPI app that stands in for
*your* backend: it holds the key, creates sessions, mints enrol tokens and reads the verdict. The apps only talk
to it and to Lumiface with tokens.

```bash
bun run dev:backend    # examples/backend on http://localhost:8010, key from LUMIFACE_KEY (default lf_sk_change-me)
```

<Tabs items={["Flutter", "React"]}>
<Tab value="Flutter">
```bash
cd examples/flutter && flutter run --release     # release: debug builds hide R8 problems on Android
```

Settings tab: the Lumiface URL (the Mac's LAN IP on a phone, `http://10.0.2.2:8000` on the Android emulator),
your backend URL (`…:8010` likewise), your subject id. The first tab has every use case; the card under it shows
what the device reported and what the backend read for itself.
</Tab>
<Tab value="React">
```bash
bun run dev:react      # examples/react on http://localhost:3010, /api proxied to :8010
```

The browser needs `https` or `localhost` for the camera. To try it on a phone over Wi‑Fi, serve the page with a
certificate and let it front the server too: `DEMO_TLS_CERT=… DEMO_TLS_KEY=… bun run dev:react` serves `https://<mac-ip>:3010`
and proxies `/v1` (with its WebSocket) to the server and `/api` to the backend, so the page's server URL is its own origin.
A self-signed CA (`openssl`, SAN = the Mac's IP) installed and trusted on the phone (Settings → General → About →
Certificate Trust Settings) is enough; the Flutter web build (`flutter run -d web-server --web-tls-cert-path …`) can use
the same `https://<mac-ip>:3010` for both URLs.
</Tab>
</Tabs>
</Step>
<Step>
## Wire it into your app

```dart
// Flutter
FaceVerifyView(
  client: LumifaceClient(baseUrl: 'https://faces.example.com'),
  sessionProvider: () async => FaceSession.fromJson(await myApi.createFaceSession()),
  onResult: (r) => myApi.faceDone(r.sessionId),
)
```

```tsx
// React
<LumifaceView
  client={new LumifaceClient({ baseUrl: "https://faces.example.com" })}
  sessionProvider={async () => sessionFromJson(await fetch("/api/face/session", { method: "POST" }).then((r) => r.json()))}
  onResult={(r) => fetch("/api/face/done", { method: "POST", body: JSON.stringify({ sessionId: r.sessionId }) })}
/>
```

Your backend: `POST /v1/sessions` with `X-API-Key` and the `subject_id` to check, hand the JSON to the app; when
the app reports done, `GET /v1/sessions/{id}` and act on `result.ok`. Two REST calls; `examples/backend` has
them in Python. Details in
[API › Authentication](/docs/api#authentication) and the [Flutter](/docs/flutter) / [React](/docs/react) pages.
</Step>
</Steps>

## What a verification looks like

The app asks for a session, opens the stream, aligns the face, moves it into the oval the server drew (`face_move`) and flashes three server-chosen colours, recording the camera the whole time (MediaRecorder on the web, H.264 from the phone encoders, streamed in chunks) with an event at each boundary. The server clocks the session itself, confirms the move from its own detector inside its window, reads the flash reflection from the frames of each colour window, runs both anti-spoof gates on the key frames it picked, matches them against the enrolled embedding and requires the same identity across them. The answer is `ok`, a `reason_code` and three scores.

Measured on 2026-09-19 with the `balanced` preset, verify against an enrolled subject, one person: Galaxy S25+ (TFLite BlazeFace) `face_move` growth 1.27–1.57 and fill 0.85–0.97, flash response 38–49 with locality 0.45–0.56, match 0.63–0.71; MacBook webcam in Chrome (tfjs BlazeFace) growth 1.20–1.30, fill 0.81–0.88, flash response 7–11 with locality 0.02–0.25, match 0.67–0.71; iPhone 12 (Apple Vision) growth 1.40–1.55, fill 0.87–0.94, flash response 16–24 with locality 0.41–0.50, match 0.68–0.72. With video (the same day, ~30 fps decoded from H.264): S25+ growth 1.40–1.51, fill 0.95–0.98, flash correlation 0.95–0.99 with locality 0.43–0.53; iPhone 12 growth 1.52–1.56, fill 0.93–0.96, flash correlation 0.73–0.97 with locality 0.32–0.45. A video of the same person replayed on a phone screen passed the oval on every device and was refused by the flash's locality (1.5–8.6).

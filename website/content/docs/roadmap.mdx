## Done

- Phase 0–3: server, Flutter package, Android and iOS, calibration scripts.
- Phase 4: hardening (CVPR gate, screen flash with locality), tested on a Galaxy S25+.
- Phase 5: Flutter web, verified on Chrome desktop.
- Phase 6: React SDK (`@lumiface/react`) with the same controller, camera source, view, hook and tests.
- SaaS shape: projects with API keys, per-project policy with presets and overrides, `client_config` in every session, admin endpoints, this documentation site with `llms.txt`.
- Phase 7: device tokens. The key stays on the backend; devices hold a session token (then also a single-use enrol token); the backend reads the verdict with `GET /v1/sessions/{id}`.
- Phase 8: the stream. `WS /v1/sessions/{id}/stream`, frames the whole time, the server clocks and judges the challenge and the flash itself; `LumifaceClient` takes only a URL; `examples/backend` shows the REST side. Run on a Galaxy S25+ release build (real person 9/10, replayed video 0/11) and on Chrome with the React example (replay 0/4), with the gesture flow of the time.
- Phase 9: the oval. `face_move` (the oval) became the only challenge; blink, smile, turn and nod, the nose parallax and the server's smile re-check were removed. Run on Chrome with the React example on 2026-09-18 (2 genuine sessions kept as the replay set).
- Phase 10: box-only detectors. MediaPipe and ML Kit were replaced by TensorFlow.js BlazeFace (short range, WASM backend) on the web, TensorFlow Lite BlazeFace bundled in the Android plugin, Apple Vision `VNDetectFaceRectanglesRequest` in the iOS plugin. The device now only has a face box (Vision adds yaw and pitch). Run on 2026-09-19 with one person: Galaxy S25+ release build (genuine 12, replay 2), Chrome on a MacBook with the React example (genuine 5 of 6, the miss at fill 0.79 became the 0.75 floor, replay 2), iPhone 12 native (genuine 3, replay 2): every genuine session passed, every phone-screen replay was refused by the flash's locality (1.5–8.6 against 0.02–0.56 for real faces). All 27 sessions are the replay set.
- Phase 11: no enrolment (2026-09-19). The subject store, enrol tokens, `FaceFlow.enroll` and the SDKs' photo capture were removed; the backend sends the person's photo as `reference_photo` with each session, the server keeps its embedding only until the device opens the stream, and nothing biometric outlives a session. The pipeline did not change; the replay set (27 genuine, 10 attack) passes as before, with the old sessions' `subjects/<id>.npy` as their reference and `reference.npy` stored per session from here on. No live round was needed: the device side sends the same stream.

## Open

- Flash thresholds were set from one person, one phone and two replays; confirm on two more people and darker phones, and try replay from a matte screen, a tablet and a monitor.
- MiniFASNet gives real faces as low as 0.31 on the S25+ in some frames (hard floor 0.30); lower `spoof_hard_floor` to 0.2 for a project if false rejects appear, CVPR and flash are the main gates.
- `face_move` thresholds were set on a Galaxy S25+ with the BlazeFace box on 2026-09-19 (one person, 5 genuine sessions: server growth 1.38–1.63 from the farthest frame, fill 0.82–0.92; 2 phone-screen replays refused by the flash's locality at 1.49–2.13, the oval itself does not stop a replay of a person walking in): `move_start_max_ratio` 0.8 (0.6 and 0.7 still made the person back off to arm's length: people overshoot the "move back" by about 20 %, two more genuine sessions at 0.7 started at 0.39 and grew 1.39–1.42), server `move_min_growth` 1.15, `move_min_fill` 0.75 (Chrome, 2026-09-19: InsightFace saw 0.79 of the oval where BlazeFace had accepted 0.85), and `max_face_width_fraction` 0.48 so that "move back" is said while aligning and the 600 ms hold stops the backing motion before the walk (frame at a distance first, then the oval). The oval is a framing step; the replay defence is the flash's locality, not the walk. Chrome and iPhone are still to be run with the new detectors.
- Video transport (2026-09-19): the SDKs record instead of sending JPEG frames. Web: MediaRecorder (WebM/VP8 on Chrome, MP4/H.264 on Safari), 250 ms chunks at 1.5 Mbps; Android: MediaCodec H.264 in the plugin, the frame rotated upright and scaled to a 640 px long side; iOS: VideoToolbox H.264 in the plugin, mirrored back for the front camera. The server decodes with PyAV into JPEG frames with both clocks, so the pipeline, the stored sessions and the replay set did not change. Verified the same night without a person: a synthetic camera (a canvas playing a stored genuine frame that walks into the oval and reflects the flash colours) ran the React example against the real server end to end over WebM and came back `OK` (117 frames decoded from 10 s, growth 1.4, flash correlation 0.998, match 0.68); the Android encoder ran as an instrumented test on the emulator's MediaCodec and the iOS encoder as an XCTest on an iPhone 12, and both streams decoded on the server into upright (Android, 360×640 from a rotated 1280×720 sensor frame) and un-mirrored (iOS) frames at the fed timestamps. First phone round with video on 2026-09-19, iPhone 12: genuine 3 of 3 (about 31 fps decoded from the H.264 stream, growth 1.52–1.56, fill 0.93–0.96, flash correlation 0.73–0.97 with locality 0.32–0.45, match 0.63–0.67), two phone-screen replays refused (`FLASH_FAIL` at locality 7.0, `MOVEMENT_MISMATCH` at fill 0.74). Galaxy S25+ the same morning: genuine 3 of 3 (about 30 fps from the hardware H.264 encoder at 360×640, growth 1.40–1.51, fill 0.95–0.98, flash correlation 0.95–0.99 with locality 0.43–0.53, match 0.64–0.67), two replays refused by the flash (locality 2.4–2.5). The replay set holds 27 genuine and 10 attack sessions. Chrome and Safari on a phone are still to be run with video.
- Each detector draws its box at its own scale against the server's InsightFace box, measured at the alignment release on 2026-09-19: Apple Vision about 1.23×, BlazeFace about 1.14× (Android and Chrome). The client thresholds are one set for all three, so an iPhone user backs off a little further (InsightFace 0.38 of the frame at release against 0.42 on Android). A per-detector scale in the SDKs would remove that; not done. CPU on iOS is not measured.
- Latex and silicone masks pass the flow (no gesture); if the threat model includes them, a gesture would have to come back with a landmark detector.

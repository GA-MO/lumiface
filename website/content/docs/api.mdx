Base path `/v1`. Project endpoints authenticate with `X-API-Key` from a backend, or a device token as `Authorization: Bearer` on the two device-facing calls (see below); admin endpoints with `X-Admin-Key`. Errors are `{"detail": {"reason_code": "...", ...}}` (or a string for framework errors). CORS is open.

## Authentication

Two credentials, two audiences:

| Credential | Header | Who holds it | Can call |
|---|---|---|---|
| Project API key (`lf_sk_…`) | `X-API-Key: <key>` | your backend | everything under `/v1` for the project |
| Session token | `hello` message on the stream | the device, for one session | `WS /sessions/{id}/stream` of that session only |
| Enrol token | `Authorization: Bearer <token>` | the device, once | `POST /subjects` for the subject fixed when the token was issued |

Never ship the project key in an app or web bundle. The loop is:

1. Backend: `POST /sessions` with the key, **with the `subject_id` it wants checked** (or none for liveness), and forwards the JSON to the device.
2. Device: opens the stream with the session token, gets the plan, streams its recording while it runs it. The subject is fixed; the stream has no field to name one.
3. Device tells the backend it is done. **Do not trust that message.**
4. Backend: `GET /sessions/{session_id}` with the key and acts on `result.ok` / `verification_id`.

The server refuses `X-API-Key` on any request whose `Origin` is a browser page other than localhost (401 `API_KEY_FROM_BROWSER`; policy `allow_browser_api_key` lifts it for a development project), and the SDKs have no place to put a key at all: `LumifaceClient` takes a URL. The key's side of the API is REST from your backend; `examples/backend` in the repository is a complete one.

A leaked session token is worth one attempt against the subject the backend chose, and it dies with the session (`ttl_seconds`). A leaked enrol token is worth one enrolment of the named subject *with whatever face the holder uploads*: only issue one to a user you have already authenticated by other means, and never for a subject that already has a face (re-enrolment needs the key; see `/subjects/tokens`).

## Subjects

| Method | Path | Body | Answer |
|---|---|---|---|
| `POST` | `/subjects` | multipart `external_id`, `name`, `photo`, `replace`, `ttl_seconds?` — or just `photo` with `Authorization: Bearer <enrol token>` | 201 subject; 409 `SUBJECT_EXISTS`; 422 with the enrolment `reason_code` or `TTL_INVALID`; 401 `ENROL_TOKEN_INVALID`; 403 `ENROL_TOKEN_MISMATCH` |
| `POST` | `/subjects/tokens` | json `{external_id, name?, ttl_seconds?, token_ttl_seconds?}` | 201 `{token, external_id, expires_at}` — single-use enrol token for a device (default life `ENROL_TOKEN_TTL_SECONDS` = 300, max one day). No `replace`: a token cannot overwrite an existing face, it gets 409; a rejected photo (422) hands the token back for a retry |
| `GET` | `/subjects` | | list |
| `GET` | `/subjects/{external_id}` | | subject or 404 `SUBJECT_NOT_FOUND` |
| `DELETE` | `/subjects/{external_id}` | | 204 |

Subject: `{external_id, name, enroll_spoof_score, created_at, expires_at}`.

`ttl_seconds` sets when the embedding is dropped; omitted it takes the policy's `subject_ttl_seconds`, `0` keeps the
subject until `DELETE`. Past `expires_at` the subject answers `SUBJECT_NOT_FOUND` on every route and the same
`external_id` can be enrolled again without `replace`; the server's retention loop deletes the row shortly after.
See [security](/docs/security#retention).

## Sessions

`POST /sessions` with `{"subject_id": "E001" | null, "purpose": "checkin"}` (project key):

```json
{
  "session_id": "3f9c…",
  "session_token": "kQx7…",
  "mode": "verify",
  "purpose": "checkin",
  "expires_at": "2026-09-18T09:01:00Z",
  "ttl_seconds": 60,
  "client_config": {
    "align_hold_ms": 600,
    "…": "…"
  }
}
```

The challenge, the oval and the flash colours are **not** in this answer. They only reach the device once it has opened the
stream, and the server judges them from what it receives, not from what the device reports.

### The stream

`WS /sessions/{id}/stream`. The full wire protocol — for porting to React Native, native or a kiosk — is on [Stream protocol](/docs/protocol); the essentials here. The device speaks first, the server answers with the plan, then the recording flows up
in chunks until the device says it is done and the server sends the verdict. The session is spent as soon as the
hello is accepted.

```
device                                            server
──────                                            ──────
{"type":"hello","token":"kQx7…","client":{…},
 "format":"webm"}                                ▶  webm | mp4 | h264 | jpeg (default)
                                                ◀ {"type":"plan","challenges":["face_move"],
                                                   "oval":{"cx":0.5,"cy":0.45,"width":0.62,"height_ratio":1.35},
                                                   "flash_colors":["ff0000","00ff00","0000ff"],
                                                   "flash_hold_ms":450,"client_config":{…}}
<binary: 8-byte big-endian device ms + chunk>  ▶  …as the recorder cuts them, whatever the phase
{"type":"event","name":"aligned","ts":…}        ▶
{"type":"event","name":"challenge_done","index":0,"ts":…} ▶
{"type":"event","name":"flash","index":0,"ts":…} ▶  …one per colour, as it is shown
{"type":"event","name":"flash_end","ts":…}      ▶
{"type":"end"}                                  ▶
                                                ◀ {"type":"result", …verdict below…}   then close
                                                ◀ {"type":"error","reason_code":"SESSION_USED"}  on refusal
```

`format` says what each binary message carries: `webm` (VP8, what MediaRecorder cuts on Chrome, Firefox and Edge,
one chunk every 250 ms) or `mp4` (H.264, Safari's MediaRecorder), which concatenate into one stream whose frame times
start at the first chunk's device time; `h264`, one Annex-B access unit per message with its own frame time (the
phone SDKs, from MediaCodec and VideoToolbox); or `jpeg`, one still per message (any client that can capture
JPEGs). The server decodes video into frames with both clocks before the pipeline runs (`services/video.py`), so the
verdict is judged the same way whatever the device sent.

What the server does with it: every frame and event is stamped with the **server's** clock on receipt; the events
only say where to look. Inside the challenge window it runs its own face detector on the frames it got and
checks that the face moved from far into the oval (`face_move`: box growth and fit, centred); the colour on the
face during each flash window is read from those frames; passive anti-spoof, identity and consistency run on the key frames it
chose. Durations (`min_session_ms`, `min_challenge_ms`, `max_challenge_ms`) are measured server-side. A feed that
repeats the same bytes is refused (`FRAMES_STATIC`). The device's `ts` values (chunk header and event `ts`) decide only which window a frame falls into — a decoded frame's device time is the chunk's time plus its offset in the video, and a phone uploads a chunk a few hundred ms after the camera took it while its events arrive at once, so placing frames by arrival would put a colour's reflection in the next colour's window — and never a duration; a client that sends no `ts` is placed by arrival.

Limits: `MAX_FRAME_BYTES` per message (4 MB), `MAX_UPLOAD_BYTES` per session (32 MB), `MAX_STREAM_CHUNKS`
messages (1800), `MAX_STREAM_FRAMES` decoded frames kept (900, a longer video is thinned evenly),
`MAX_IMAGE_PIXELS` per decoded frame (20 Mpx). Chunks beyond what the link can carry are dropped by the SDKs
rather than queued.

Answer:

```json
{
  "ok": true,
  "mode": "verify",
  "reason_code": "OK",
  "scores": { "match": 0.71, "spoof": 0.93, "consistency": 0.88 },
  "verification_id": 42,
  "details": {}
}
```

`details` is empty for the device; the backend sees the server's windows, the `face_move` readings, flash scores and key frames in the audit log — every gate's score is there whatever the verdict (`GET /verifications` is the summary, the row's `details` the full record; see [the `details` object](/docs/reason-codes#the-details-object)). Refusals arrive as `{"type":"error","reason_code":…}` and close the socket: `SESSION_NOT_FOUND`, `SESSION_USED`, `SESSION_EXPIRED`, `HELLO_INVALID`, `EVENT_INVALID`, `PAYLOAD_TOO_LARGE` (close code 1009). A frame that does not decode is skipped; a window with no usable frame ends as `NO_FACE`, no frames at all as `FRAME_COUNT`.

`GET /sessions/{id}` (project key) is how the backend learns the outcome; `result` is the verify answer above, or `null` while nothing was uploaded:

```json
{
  "session_id": "3f9c…",
  "mode": "verify",
  "subject_id": "E001",
  "purpose": "checkin",
  "used": true,
  "expires_at": "2026-09-18T09:01:00Z",
  "result": { "ok": true, "mode": "verify", "reason_code": "OK", "scores": { "…": "…" }, "verification_id": 42 }
}
```

| Method | Path | Body | Answer |
|---|---|---|---|
| `GET` | `/policy` | | `{project, preset, overrides, effective}` |
| `PUT` | `/policy` | `{preset?, overrides?, merge?}` | same; 422 `UNKNOWN_PRESET` / `POLICY_INVALID` |

| Method | Path | Body | Answer |
|---|---|---|---|
| `POST` | `/projects` | `{name, preset?}` | 201 `{id, name, preset, api_key, ...}` |
| `GET` | `/projects` | | list with counts, no keys |

## Debug

`POST /debug/score` (multipart `photo`, `DEBUG=1` only): per face `bbox`, `det_score`, `yaw`, `pitch`, `roll`, `spoof_real`, `spoof_per_model`, `cvpr_live`, `embedding`.

## Health

`GET /health` → `{"ok": true, "presets": ["balanced", "strict", "relaxed", "emulator"]}`.

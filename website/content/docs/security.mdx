title: Security model
description: What Lumiface stops, what it does not, the numbers behind the thresholds, and how to deploy it safely.
---

Lumiface is not certified liveness (no ISO 30107-3 evaluation). It is a layered defence that was measured against printed photos, phone and monitor replays, cut-outs, paper masks and latex or silicone masks.

## Layers

1. **Random challenges with timing** on the device: a blink must last 40–600 ms, each challenge at least 300 ms and at most 5 s, the whole session at least 1.5 s. A prerecorded video reacts at random times; a still photo cannot blink.
2. **Nose parallax** during every session (a client-only turn is added when the server picked none): a real head shifts the nose against the eyes by about 0.11–0.15 at 25° of yaw; a rotated print or screen shifts it by 0.026.
3. **Passive anti-spoof** on the server for every frame: MiniFASNet V2 + V1SE (needs a hard floor per frame and a mean), then the CVPR-2024 ResNet50 on a face crop with margin 0.3, which catches bezel-free screen replay (replay ≤ 0.015 against genuine ≥ 0.30).
4. **Screen flash**: three random saturated colours chosen by the server, one frame each; the hue shift on the cheeks must correlate with the commanded sequence and beat every other permutation, and the surroundings may reflect at most 0.8× what the face does (real faces 0.47–0.52 on a phone, 0.04 on a laptop; a replayed phone screen 1.15–2.31 because the whole sheet reflects).
5. **Smile re-check** from 68 landmarks: a rigid mask passes both passive gates and cannot smile. Mouth width gain ≥ 1.08 or corner lift ≥ 0.04 (genuine 1.14–1.24 and 0.068–0.073).
6. **Identity**: every frame ≥ `match_threshold` against the enrolled embedding, and every pair of frames ≥ 0.60 (0.40 when one is mid turn or nod) against each other.

## Measured results

| Material | Result |
|---|---|
| Genuine (AxonData 14 sessions, team phones, emulator, MacBook) | pass |
| Phone and monitor replay (12) | 0 pass |
| Cut-outs (5), paper masks (5) | 0 pass |
| Latex (3), silicone (3) masks | pass both passive gates; stopped only by the smile challenge |
| Still photo rotated in front of the camera | never satisfies the turn (parallax) |

## Not covered

- **A compromised device.** Every server gate scores the pixels the device sends, and the device learns the challenges and the flash colours from the plan so it can run the flow. Since the flow is streamed, the server judges everything from its own evidence: it clocks the session itself, confirms each blink, smile, turn or nod from its own landmarks on the frames inside each window, reads the flash reflection from the frames of each colour window, and rejects a feed that repeats bytes. A patched client therefore cannot skip checks or forge timings; what it can still do is *inject video*: play prepared footage of the victim performing the plan, with the colours painted on, through a virtual camera fast enough to follow the plan live. What is left against that is the passive anti-spoof on every key frame, the consistency of the injected footage with itself, and the ArcFace match. The device tokens do not change this: they bound *what* a leaked credential can do, not *whether* the device is honest. Where the device is the adversary, pair Lumiface with platform attestation (Play Integrity, App Attest) and treat the `relaxed` and `emulator` presets, which switch the flash and smile gates to score-only, as development settings.
- Real-time deepfakes injected as a virtual camera: the same point in a different costume.
- 3D masks that can articulate a mouth.
- Twins.

## Deploying safely

- Keep the server private (VPN, allow-list) and terminate TLS in front of it.
- The project API key stays on your backend. Devices only ever hold a **session token** (issued with the session, good for that one verify of the subject the backend chose) or a single-use **enrol token** (`POST /v1/subjects/tokens`); see [API authentication](/docs/api#authentication). A key embedded in an app or web bundle lets anyone list and delete subjects, read every verification and lower the policy's thresholds — so three things make that hard to do by accident: the device SDKs (`LumifaceClient`) cannot take a key, the server-side clients throw in a browser and live in a separate import, and the server answers 401 `API_KEY_FROM_BROWSER` to a key sent from any page but localhost. Keys start with `lf_sk_` so secret scanners catch them in a repo.
- Read the outcome yourself: after the device reports "done", call `GET /v1/sessions/{id}` with the key. The device's copy of the answer is just bytes it can edit.
- An enrol token binds the *identity*, not the *face*: whoever holds it enrols their own face as that subject. Issue one only after your own authentication of that user, and never for a subject that already has a face (the server refuses; re-enrol with the key after a `DELETE`).
- Streams are capped (`MAX_FRAME_BYTES` per frame, `MAX_UPLOAD_BYTES` and `MAX_STREAM_FRAMES` per session, `MAX_IMAGE_PIXELS` per decoded frame) and die with the session's TTL; enrolment uploads by `MAX_UPLOAD_BYTES`.
- `STORE_FRAMES=1` writes every streamed frame of failed attempts to `FRAMES_DIR/<project>/<session>/`; nothing deletes them, so keep it off in production or purge the directory yourself.
- One project per app and per environment, so `relaxed` on a developer laptop never applies to production.
- Set `ADMIN_API_KEY` only where project management runs; rotate keys with `POST /v1/projects/{id}/rotate-key`.
- Leave `DEBUG=0` and `STORE_FRAMES=0` in production; both keep or return more than the verdict.
- Embeddings are biometric data: keep the database encrypted at rest and delete subjects when people leave (`DELETE /v1/subjects/{id}`) or give them an expiry (see below).
- The InsightFace `buffalo_l` weights are non-commercial research only.

## Retention

Nothing biometric has to live forever on the server:

- **Subjects** carry an optional `expires_at`. `POST /v1/subjects` takes `ttl_seconds`; when omitted the project policy's
  `subject_ttl_seconds` applies (`0` keeps the subject until `DELETE`). One-shot flows such as KYC against an ID photo
  can enrol with a TTL of minutes; attendance keeps `0` and deletes on offboarding.
- **Sessions** are single use and expire after `session_ttl_seconds`; the row stays `SESSION_PURGE_GRACE_SECONDS`
  (default one hour) so a late client still sees `SESSION_EXPIRED`.
- A **purge loop** runs every `RETENTION_INTERVAL_SECONDS` (default 300, `0` disables) and deletes expired subjects and
  spent sessions. An expired subject is already invisible to the API before the purge reaches it.
- **Verifications** are the audit log and are kept; the purge only clears their link to a deleted embedding
  (`subject_id`) while `subject_external_id` and the scores remain.
